# ls-sdd-clarify — Clarify a Specification

**Conventions**: Read `ls-sdd` (§ Directory Layout through § Templates) for directory structure, frontmatter, status, slug, and ID format. Also read § Research and Delegation; it applies regardless of that reading range. Skip § What's Next? — it is only for direct `ls-sdd` invocation.

## Purpose

Surface gaps in a `draft` spec **before** planning. A spec that looks complete
almost always has hidden ambiguity: edge cases, error behavior, scale
assumptions, undefined terms. This skill asks a structured set of questions,
records the answers, and advances the spec to `clarified`.

## When to Use

- A spec is in `draft` and the user wants to move toward planning.
- The user explicitly asks to "clarify", "stress-test", or "find gaps" in a spec.

Do **not** use this skill to rewrite the spec — that is `ls-sdd-specify`. This
skill only adds a `clarifications.md` and updates the spec's status.

## Procedure

1. **Identify the target spec.** If the user did not name one:
   - Scan `specs/` for specs in `draft` status.
   - If exactly one, use it. If multiple, ask the user which one.
   - If none, recommend `ls-sdd-specify` first.

2. **Read the spec** (`specs/NNNN-spec-<slug>/spec.md`) and its frontmatter.
   Note the `scale` — `enterprise` specs deserve deeper non-functional probing
   than `trivial` ones.

3. **Read the constitution** (`AGENTS.md`) if it exists, for context on
   quality bar and architecture guardrails.

4. **Separate factual gaps from user decisions.** Classify unresolved points as either (a) facts that can be checked in the codebase or official, version-appropriate documentation, or (b) product, priority, or policy decisions that only the user can make. Delegate only the relevant factual checks, with a bounded read-only scope and evidence. Use findings to resolve factual uncertainty or to present a new contradiction; do not replace missing evidence with a guess. Ask the user about decisions and any remaining ambiguity.

   **Ask structured questions** in these categories. Ask one block; let the
   user answer in bulk. Skip categories that the spec already covers
   thoroughly, and do not ask the user to answer factual questions that the
   delegated research has already resolved.

   - **Edge cases**: What happens at the boundaries? Empty input, zero, max
     length, concurrent access, offline, expired tokens, partial failure.
   - **Error handling**: What errors are expected? How are they surfaced to
     the user / caller? Are they retried, logged, escalated?
   - **Non-functional requirements** (especially for `scale: enterprise`):
     Performance targets, latency budgets, throughput, security (authn/authz,
     data classification), scalability (vertical / horizontal limits),
     observability (logs, metrics, traces).
   - **Scale & growth**: Expected volume now, in 6 months, in a year. What
     breaks first?
   - **Ambiguity**: Terms in the spec that could mean more than one thing.
     "User", "session", "document", "valid" — pin them down.
   - **Integration**: What does this depend on? What depends on this? Are
     there contracts that must not break?
   - **Out of scope (revisited)**: Things that *look* in scope but should be
     explicitly excluded.

5. **Write the answers** to `specs/NNNN-spec-<slug>/clarifications.md`:

   ```markdown
   # Clarifications: <Spec Title>

   > Generated by ls-sdd-clarify on YYYY-MM-DD.

   ## Edge Cases
   - Q: ... A: ...

   ## Error Handling
   - Q: ... A: ...

   ## Non-Functional Requirements
   - Q: ... A: ...

   ## Scale & Growth
   - Q: ... A: ...

   ## Ambiguity
   - Q: ... A: ...

   ## Integration
   - Q: ... A: ...

   ## Out of Scope (revisited)
   - Q: ... A: ...
   ```

   Omit categories that produced no new information. Keep the Q/A format — it
   makes the reasoning traceable later.

6. **Update the spec frontmatter**: set `status: clarified`. Do **not** edit
   the spec body — the clarifications live in the separate file. If a
   clarification contradicts the spec body, flag it to the user and ask
   whether to amend the spec via `ls-sdd-specify`.

7. **Confirm to the user**: print the clarifications path, the count of
   questions asked/answered, and recommend the next step:
   - If `scale: trivial` and no major gaps: recommend `ls-sdd-create-plan` (minimal plan) then `ls-sdd-tasklist` directly.
   - Otherwise: recommend `ls-sdd-create-plan`.

## Language

→ See `ls-sdd` § Language. Write all artifacts in the project's artifact language (from `AGENTS.md`).

## What Not to Do

- Do not rewrite the spec body. Clarifications are additive.
- Do not skip categories silently — if a category produced no questions, note "no new questions" rather than omitting without trace. Keep unresolved factual uncertainty explicit and cite evidence when reporting a contradiction.
- Do not advance the spec to `clarified` if the user could not answer critical questions; leave it in `draft` and list the open items.
